# Day 10: Combinatorics -- Permutations, Combinations, Counting Principles

## Why This Exists

When you analyze an algorithm's complexity, you are counting things. How many
possible inputs exist? How many states can a search explore? How many ways can
you arrange elements? Combinatorics is the mathematics of counting, and it is
the foundation of algorithm analysis.

Consider sorting: there are n! permutations of n elements, which means any
comparison-based sort must make at least log2(n!) comparisons. That is the
information-theoretic lower bound -- you cannot beat it, period. Understanding
why requires combinatorics.

Password security? A password of length 8 from 62 characters (a-z, A-Z, 0-9)
has 62^8 = 218 trillion possibilities. Add one more character and you multiply
by 62. Combinatorics tells you exactly how secure your system is.

Database query optimization? The number of possible join orderings for n tables
is n!, which is why optimizers use heuristics beyond ~10 tables. Combinatorics
tells you when brute force becomes impossible.

This is not abstract math. It is the language of computational feasibility.

### What If This Didn't Exist?
Without combinatorics, you cannot analyze algorithm complexity or know when brute force is hopeless. Before counting principles were formalized, engineers guessed whether exhaustive search was feasible. A database optimizer without combinatorial analysis would try all n! join orderings for 15 tables -- that is 1.3 trillion plans, turning a millisecond query into hours. Password policies would be set by intuition rather than mathematics. You would have no way to prove that comparison-based sorting cannot beat O(n log n), because that lower bound is derived from the fact that there are n! permutations and each comparison eliminates at most half.

### Why This Name?
The word "combinatorics" comes from the Latin "combinare," meaning "to combine two by two." The field was formalized in the 17th century by Blaise Pascal (Pascal's Triangle, 1654) and later by Leibniz, who used "ars combinatoria" in 1666 to describe the science of counting arrangements. "Permutation" comes from Latin "permutare" (to change thoroughly), reflecting complete rearrangement. "Combination" comes from Latin "combinatio," emphasizing selection without regard to order. The distinction between permutations and combinations -- whether order matters -- is the first fork in every counting problem.

### The Physics Connection
Combinatorics connects to physics through the enumeration of microstates. In thermodynamics, entropy is proportional to the logarithm of the number of microstates -- a combinatorial quantity. In computing hardware, a CPU with a 64-bit address bus can address 2^64 memory locations, a direct application of the counting principle. Cache behavior depends on how many ways data can be mapped to cache lines (set-associative caches use C(ways, 1) per set). The heat generated by a brute-force search over n! states is proportional to the number of operations, making combinatorial explosion a literal energy problem.

### The Mathematics Connection
The information-theoretic lower bound for comparison sorting is ceil(log2(n!)), which comes directly from combinatorics -- you need enough comparisons to distinguish all n! permutations. Stirling's approximation (n! ~ sqrt(2*pi*n) * (n/e)^n) bridges combinatorics and analysis, giving us the n*log(n) lower bound. The pigeonhole principle, a combinatorial argument, proves that any lossless compression must make some inputs larger. Ramsey theory shows that sufficiently large structures inevitably contain ordered substructures -- impossibility results rooted in counting.

### The Economics Connection
Combinatorial explosion is the reason NP-hard problems matter economically. The traveling salesman problem for 20 cities has 20!/2 orderings -- about 10^18. You could buy every GPU on Earth and still not brute-force it in a lifetime. This trade-off drives the entire approximation algorithm industry: companies pay for 95%-optimal solutions in polynomial time rather than optimal solutions in factorial time. Memory vs. speed appears in Pascal's Triangle: you can precompute binomial coefficients in O(n*k) space, or recompute them each time in O(1) space but O(k) time per query.

### When Does This Break?
Combinatorial formulas assume independence and uniform distribution, which real systems violate constantly. If password characters are not chosen uniformly (people pick "password123"), the effective keyspace is orders of magnitude smaller than 62^n. Floating-point overflow kills naive factorial computation around n=170 for 64-bit doubles. Generating all permutations is feasible for n~10 but physically impossible for n=20 (20! > 2.4 * 10^18 operations). Multinomial coefficients with repeated elements require careful division to avoid overcounting -- forgetting this is a classic source of bugs in competitive programming.

### When Should You Violate This?
When your problem has structure that makes counting unnecessary. If you need to find one valid arrangement, backtracking with pruning often beats enumerating all possibilities. Randomized algorithms (like the next day's Miller-Rabin) bypass exhaustive counting by sampling. When approximate answers suffice, Monte Carlo methods estimate combinatorial quantities without computing them exactly. For problems with overlapping subproblems (like counting paths in a grid), dynamic programming replaces exponential enumeration with polynomial-time computation. The moment you see repeated substructure, stop counting and start memoizing.

## Theory (40 min)

### 1. Fundamental Counting Principles

**Rule of Product (AND)**: If task A has m ways and task B has n ways, then
doing A AND B has m * n ways. (Choose a shirt from 5 AND pants from 3 = 15 outfits.)

**Rule of Sum (OR)**: If task A has m ways and task B has n ways (mutually exclusive),
then doing A OR B has m + n ways. (Take bus with 3 routes OR train with 2 routes = 5 options.)

Everything in combinatorics builds on these two rules.

### 2. Permutations (Order Matters)

A permutation is an ordered arrangement. The number of ways to arrange n distinct
objects is n! = n * (n-1) * (n-2) * ... * 1.

Why? For the first position you have n choices, for the second n-1, and so on.
By the rule of product: n * (n-1) * ... * 1 = n!

**k-permutations**: The number of ways to choose and arrange k items from n:
P(n, k) = n! / (n-k)!

### 3. Combinations (Order Doesn't Matter)

A combination is an unordered selection. "Choose 3 from 5" counts {A,B,C} and
{C,B,A} as the same selection.

C(n, k) = n! / (k! * (n-k)!)

Why divide by k!? Because each combination corresponds to k! permutations
(k! ways to order the chosen items), and we want to count each group once.

### 4. Binomial Coefficients and Pascal's Triangle

C(n, k) is also called "n choose k" or the binomial coefficient. It satisfies:
    C(n, k) = C(n-1, k-1) + C(n-1, k)

This is Pascal's Triangle. Each entry is the sum of the two entries above it.
This recurrence gives us an O(n*k) dynamic programming algorithm, avoiding
factorial overflow for large n.

### 5. Generating Permutations and Combinations (Backtracking)

Algorithms often need to enumerate all permutations or combinations, not just
count them. The standard technique is backtracking: build a solution element by
element, and undo each choice before trying the next.

### 6. Stars and Bars

"How many ways to put n identical balls into k distinct boxes?" is equivalent
to "how many solutions to x1 + x2 + ... + xk = n with xi >= 0?"

Answer: C(n + k - 1, k - 1). Visualize n stars (balls) and k-1 bars (dividers).
